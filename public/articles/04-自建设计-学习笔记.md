## 关键设计决策

### 1. 价格用整数 (int64_t)

```cpp
using Price  = int64_t;  // 单位：分
using Amount = int64_t;  // 单位：分
```

**为什么不用 float/double？**
- `0.1 + 0.2 != 0.3` 在浮点数中是真的
- 金融系统要求精确计算，一分钱都不能差
- 参考：Java 版全部用 `BigDecimal`

### 2. 订单簿用 std::map + 自定义比较器

```cpp
// 买盘：价格从高到低
struct BuyComparator {
    bool operator()(const OrderKey& a, const OrderKey& b) const {
        if (a.price != b.price) return a.price > b.price;  // 高价优先
        return a.sequenceId < b.sequenceId;                 // 同价时间优先
    }
};

using BuyBook = std::map<OrderKey, shared_ptr<Order>, BuyComparator>;
```

**为什么用 std::map？**
- 自动按 key 排序 → `begin()` 就是最优价
- 插入/删除 O(log n)
- 对应 Java 版的 `TreeMap`

**设计演进**：初版 `OrderBook` 为单类，内部同时持有 `buyBook_`/`sellBook_` 两个 map（用 `side_` 字段区分），任一时刻必有一个空转。后拆分为「抽象基类 `OrderBook` + `BuyOrderBook`/`SellOrderBook` 两个子类」，各自只持有一个 map，消除冗余字段，买/卖盘排序差异固化到各自类中。

### 3. 订单状态机

```
PENDING_NEW ──submit──▶ NEW ──match──▶ PARTIALLY_FILLED ──match──▶ FILLED
    │                    │                    │
    └──reject──▶ REJECTED ├──cancel──▶ CANCELED ├──cancel──▶ CANCELED
                          │                    │
                          └──expire──▶ EXPIRED └──expire──▶ EXPIRED
```

**终态（不可再变更）**：FILLED / CANCELED / REJECTED / EXPIRED
**可撤销**：PENDING_NEW / NEW / PARTIALLY_FILLED

### 4. 加权均价增量计算

```
新均价 = (旧均价 × 旧数量 + 新价格 × 新数量) / (旧数量 + 新数量)
```

O(1) 时间复杂度，不需要遍历全部成交记录重算。

### 5. 线程安全

每个 Manager/Engine 内部持有一个 `std::mutex`，public 方法加 `std::lock_guard`。
这是一个简化方案——生产环境会按更细粒度锁或 Lock-Free 设计。

## 实现心得与踩坑记录

> 记录自建 OMS 实现过程中踩过的坑，供日后回顾。

### 一、C++ 语言层

1. **纯虚析构必须有定义**：`virtual ~OrderBook() = 0;` 会导致链接错误（派生类析构时要调用基类析构）。接口类直接用 `virtual ~OrderBook() = default;`。

2. **const 方法里不能用 `operator[]`**：`std::unordered_map::operator[]` 在 key 不存在时会插入默认值（改变容器），所以它不是 const。const 上下文读 map 用 `find()` 或 `at()`，否则报 `discards qualifiers`。

3. **默认参数只在声明处写一次**：头文件声明里写了 `= 10`，.cpp 定义里就不能再写，否则编译错误。

4. **非 inline 函数别放头文件**：`utils.hpp` 里的 `get_now_timestamp_ns()` 若不加 `inline` + `#pragma once`，被多个翻译单元包含会 ODR violation 链接错误。

5. **`std::mutex` 非递归**：`submitOrder` 已持 `mtx_` 时，内部不能再调会加锁的 `processFill`（死锁）。要么拆「加锁公开方法 + 无锁私有核心」，要么持锁时直接操作成员。

6. **聚合初始化易错**：`Order` 字段多，`Order{...}` 聚合初始化容易因字段顺序出错。用 `make_shared` + 逐字段赋值更稳。

### 二、设计判断层

7. **「拆抽象基类」和「用基类引用」是两个方向**：`OrderBook` 拆成 `BuyOrderBook`/`SellOrderBook` 解决**实现层**冗余（单类双 map 空转）；`match(OrderBook&)` 用基类引用解决**调用层**复用（一份撮合逻辑覆盖买卖两向）。一个向内看存储，一个向外看接口。

8. **职责边界：engine 管状态 vs OrderManager 管日志会丢 beforeState**：撮合引擎撮合时已更新 `filledQty`/`state`，OrderManager 记日志时 `beforeState` 读到的是改之后的值，日志丢失了「从 X 状态流转到 Y」的信息。彻底解法：engine 只改 `filledQty`+订单簿，`state` 全归 OrderManager。

9. **骨架转实现要清死代码**：骨架里 `(void)` 抑制未用参数，实现后参数被用到，`(void)` 变成死代码（`return` 之后的语句甚至不可达）。实现完记得删。

### 三、金融/业务层

10. **成交价以 maker 为准**：taker 被动接受 maker 报价，`marketPrice = maker.price`，不是 taker 限价。

11. **市价单 price 设极端值**：市价买单 `INT64_MAX`（吃任何卖价）、市价卖单 `0`（吃任何买价），确保 `priceCrosses` 恒成立。但剩余挂单时 price 会停在极端档位。

12. **卖出不改变剩余持仓成本价**：`reducePosition` 只减 `totalQty`/`availableQty`，`avgCostPrice` 不动。

13. **冻结 vs 减仓**：`freezeQuantity` 只减 `availableQty`（下单锁定），`reducePosition` 两个都减（成交真实减仓）。一个管「锁」，一个管「真卖」。

### 四、遗留方向（非 bug）

- `OrderManager` 未持有 `PositionManager`/`RiskManager`，集成靠 main.cpp 手动编排 → 可引入 Orchestrator 串起「风控→撮合→持仓」全链路。
- 日志 `beforeState` 语义（见第 8 条）→ 重构职责边界，让 engine 只管撮合。
- `checkCancelRate` 无时间窗口，仅固定阈值计数 → 引入滑动时间窗。
- 撮合引擎粗粒度锁（整引擎一把 `mutex`）→ 价格档位锁 / Lock-free。
