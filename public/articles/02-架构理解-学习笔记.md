## 一、华泰证券交易系统通信框架（XSTEP协议）

### 1.1 系统总体架构

```
客户端 → NGINX代理 → 网关服务组 → OMS(订单管理系统) → DownStream(报盘) → 柜台/交易所
                                          ↓
                                      订阅中心（推送成交回报回客户端）
```

- **外部系统**：必须通过NGINX代理访问网关
- **内部系统**：通过XSTEP服务发现机制，直接对目标服务发起访问

### 1.2 XSTEP协议：分层设计

XSTEP是华泰**自研通信协议**，核心分层：

| 层次 | 职责 | 关键技术决策 |
|------|------|-------------|
| **会话层** | 连接管理、心跳、安全 | 信任TCP可靠传输，异常时中断重连，**不重传消息**；支持TLS加密/非加密两种模式 |
| **应用层** | 业务数据承载 | Event(`MAP<K,V>`键值对) + Group(数组嵌套，树形无限扩展)；可与Dubbo混合部署 |

#### 会话层关键设计

- **心跳机制**：T间隔 × 3次无报文 → 中断链路
- **安全防护**：规定最大报文长度，超限丢弃 → 防恶意攻击
- **自动重连**：支持自定义策略
- **服务发现**：内置服务发现与路由能力

#### 应用层数据模型

```
Event: MAP<K, V> — 支持所有基础数据类型
Group: 数组 + 嵌套 → 可无限扩展成树形结构
```

> **混合部署**: 业务系统可全部用XSTEP，也可**会话层Dubbo + 应用层XSTEP**组合使用

### 1.3 服务发现与路由 — 五大原则

1. 服务的消费者**不应感知**具体服务提供者的变化
2. 支持**负载均衡访问**
3. 支持**主备访问**
4. 支持**服务分组**（隔离不同用户/业务/版本）
5. 支持**灰度升级**（按版本划分分片，部分升级，用户逐步切换）

### 1.4 OMS分片架构

- **内存交易系统**：追求低延迟
- **水平分片**：基于用户或业务（A股OMS、期权OMS）切分
- **高可用**：分片内主备机切换
- **灰度发布**：按版本划分分片，用户逐步迁移

### 1.5 关键子系统

| 子系统 | 功能 |
|--------|------|
| **网关(Gateway)** | 外部入口，协议接入、流量控制、权限控制 |
| **OMS** | 内存交易核心，分片扩展 |
| **DownStream(报盘)** | 多节点面向不同柜台/交易所，向上游屏蔽差异 |
| **订阅中心** | 订阅维度和过滤，成交回报快速回到客户端 |

### 1.6 性能数据

- 系统延迟降低 **85%**
- 清算效率提升 **70%**
- 订阅中心: 380 TPS → **6000 TPS**（15倍提升）
- 跨地域数据同步延迟 < **100ms**
- 覆盖宁沪深港**多地多交易中心**分布式集群

## 二、华泰证券事件驱动型微服务架构

### 2.1 为什么不用传统RPC微服务？

| 问题 | RPC微服务 | 事件驱动 |
|------|----------|---------|
| **耦合** | 上下游强依赖，下游故障拖垮上游 | 异步解耦，独立自治 |
| **调用链** | 极长，降低稳定性和TPS | 事件广播，一对多 |
| **数据库** | 中心化瓶颈，难以横向扩展 | 服务本地数据自治 |
| **接口膨胀** | API数量无限增长 | 按事件类型收敛 |
| **延迟** | 同步等待 | 异步处理，微秒级 |

### 2.2 核心架构转变

1. **异步化**：无需同步等待，避免上下游依赖和长调用链
2. **数据自治**：服务自己订阅事件 → 本地保存数据 → 本地调用

### 2.3 事件三种类型

| 类型 | 用途 |
|------|------|
| **Data事件** | 有状态变更，Data驱动 |
| **Command事件** | 无状态变更，Request驱动 |
| **Query事件** | 数据查询 |

### 2.4 天然的CQRS模式

事件驱动天然实现**命令查询职责分离(CQRS)**：

```
模式一：本地缓存(Local Cache) → 读取加速，含启动恢复机制
模式二：旁路集中存储 → 获取未缓存数据，支撑内存状态恢复
模式三：可选快照文件 → 加速数据获取
```

### 2.5 Kafka实践要点

- **可靠性**：分区 + 副本(≥2) + 容错
- **可扩展性**：集群规模热扩展
- **Consumer控制**：Partition offset由Consumer管理，支持回溯和重设
- **流式物化**：Append-only（历史回放）和Upsert两种模式

### 2.6 EDA面临的挑战

1. 分布式事务难以支持
2. 异步通讯比同步调用更需精细管理
3. 总线天生的集中式风险

## 三、OMS父子订单拆分（TechNova系列）

### 3.1 核心概念

```
机构投资者下单
      ↓
  【父订单（母单）】← 仅存在于OMS内部，定义总体目标
  "2小时内买入100万股，VWAP策略"
      ↓ TWAP/VWAP算法引擎动态拆分
  【子订单1】【子订单2】...【子订单N】← 实际发往交易所
```

- **父订单**：不进入交易所，定义总目标+约束（数量、时间窗口、策略类型）
- **子订单**：算法引擎动态生成的交易所实际指令

### 3.2 为什么需要拆单

| 问题 | 后果 |
|------|------|
| **市场冲击** | 巨额订单瞬间消耗对手方流动性，成交均价严重偏离市价（滑点） |
| **信息泄露** | 大单暴露意图，引发HFT抢跑（Front-running） |
| **流动性不足** | 单个时点可能不存在足够对手盘 |

### 3.3 核心算法：TWAP vs VWAP

| 维度 | TWAP | VWAP |
|------|------|------|
| **全称** | 时间加权平均价格 | 成交量加权平均价格 |
| **原理** | 总时间T → N个时间片，每片执行Q/N | 模仿市场成交量分布节奏执行 |
| **依赖** | 无（开环控制） | 需实时Tick数据 + 历史Volume Profile |
| **优点** | 简单、确定性高 | 智能、隐藏在市场波动中、冲击成本低 |
| **缺点** | 忽略成交量节奏，清淡时段不必要冲击 | 实现复杂，依赖实时数据质量 |

### 3.4 关键技术挑战与设计

| 挑战 | 设计方案 |
|------|---------|
| **状态一致性** | 子订单成交异步/乱序到达 → 原子性聚合到父订单 |
| **并发控制** | 多笔成交回报并发更新 → 乐观锁/悲观锁或DB原子操作 |
| **AvgPx精度** | 使用**BigDecimal/缩放整数**，**严禁float/double**；增量计算避免全量重算 |
| **低延迟** | 算法毫秒级决策，子订单微秒级发送 |
| **高可用** | 执行中父订单不受单点故障影响，支持故障恢复与状态续传 |
| **幂等性** | 成交回报可能重复，必须幂等处理，防止超买/超卖 |

### 3.5 架构分层

```
接入层 ───── 接收父订单指令，风控预检
  ↓
算法引擎层 ── 根据策略(TWAP/VWAP)生成子订单序列，实时响应市场数据
  ↓
执行网关层 ── 子订单低延迟发送至交易所/SOR，接收成交回报
  ↓
状态聚合层 ── 子订单成交回报聚合更新父订单状态，实时监控
  ↓
持久化层 ─── 存储订单全生命周期数据，支持事后分析和清算
```

## 四、多市场接入OMS聚合架构（TechNova系列）

### 4.1 核心痛点

当机构从单一市场（如仅A股）扩展到港股、美股时：

| 挑战 | 具体表现 |
|------|---------|
| **协议异构** | A股私有协议 vs 港股美股FIX(4.2/4.4/5.0多版本)，不同券商有各自"方言" |
| **交易规则差异** | T+0(港股/美股) vs T+1(A股)，交易时间、最小变动单位、涨跌幅各不相同 |
| **数据模型不统一** | 同一股票在不同市场代码表示不同，订单状态/错误码语义千差万别 |
| **风控盲点** | 孤立系统无法实时汇总跨市场持仓和风险敞口 → 全局性风控漏洞 |

### 4.2 三大核心设计原则

#### 原则一：适配器模式 — 解决协议异构

```
                         ┌─→ [港股FIX适配器] → 港交所
内部标准订单模型 ──→ 路由层 ──┼─→ [美股FIX适配器] → 美股交易所
                         ├─→ [A股STEP适配器] → 上交所
                         └─→ [A股BINARY适配器] → 深交所
```

- 每个市场构建独立 **Market Gateway**
- **出口方向**：内部标准订单 → 特定市场协议
- **入口方向**：市场成交回报 → 统一内部事件

#### 原则二：有限状态机 — 统一订单生命周期

所有市场映射到统一状态模型：

```
PendingNew → New → PartiallyFilled → Filled
                 → Canceled
                 → Rejected
```

严格定义状态、事件和转移路径，防止跨市场状态混乱。

#### 原则三：事件驱动架构 — 高并发与解耦

```
OMS发布 "order_created" → Kafka
  → RMS订阅 → 风险评估 → "order_approved/rejected"
  → 清算订阅 → 成交处理 → "settlement_complete"
  → 风控订阅 → 跨市场敞口汇总
```

### 4.3 统一风控与头寸视图

聚合层实时汇总所有市场（A股+港股+美股）的：
- 持仓
- 风险敞口
- 盈亏

→ 进行**全局额度控制**和**跨市场熔断**

### 4.4 商业OMS产品参考

| 产品 | 特点 |
|------|------|
| **FlexTrade FlexOMS** | 全球多资产OMS，MiFID II/RegNMS合规 |
| **FIS OMS** | 合并全球交易视图，多资产执行 |
| **Eze OMS** | 500+执行场所，实时跨市场盈亏 |
| **AlphaDesk(LSEG)** | 云原生OMS+PMS，多币种多托管人 |

## 五、FIX协议核心原理

### 5.1 消息结构

```
每条FIX消息 = Header + Body + Trailer
字段格式: Tag=Value
分隔符: SOH (ASCII 0x01, 显示为|)
```

| 部分 | 作用 | 关键字段 |
|------|------|---------|
| **Header** | 路由和身份识别 | 8(BeginString), 35(MsgType), 49(SenderCompID), 56(TargetCompID), 34(MsgSeqNum), 52(SendingTime) |
| **Body** | 业务数据 | 55(Symbol), 54(Side), 44(Price), 38(OrderQty) |
| **Trailer** | 完整性校验 | 10(CheckSum) ← 永远是最后字段 |

### 5.2 消息示例

```
8=FIX.4.4|9=65|35=A|49=TESTFIX|56=LMXBDM|34=1|52=20120924-14:05:44.952|10=062|
```

逐字段解析：
```
8=FIX.4.4          ← 协议版本（永远是第一条）
9=65               ← 消息体长度(35到10之前)
35=A               ← 消息类型: Logon(登录)
49=TESTFIX          ← 发送方ID
56=LMXBDM           ← 接收方ID
34=1               ← 序列号
52=20120924-14:05:44.952  ← 发送时间
10=062             ← 校验和(永远是最后一条，Sum(ASCII)%256)
```

### 5.3 关键消息类型

| MsgType(35) | 消息名 | 类别 | 用途 |
|-------------|--------|------|------|
| A | Logon | 管理 | 登录建立会话 |
| 5 | Logout | 管理 | 注销结束会话 |
| 0 | Heartbeat | 管理 | 心跳保活 |
| **D** | **NewOrderSingle** | 应用 | **新订单（最重要的下单消息）** |
| G | OrderCancel/ReplaceRequest | 应用 | 改单请求 |
| F | OrderCancelRequest | 应用 | 撤单请求 |
| **8** | **ExecutionReport** | 应用 | **执行报告（最重要的回报消息）** |
| 9 | OrderCancelReject | 应用 | 撤单拒绝 |

### 5.4 会话生命周期

```
1. 建立TCP连接
2. Initiator发送 Logon(35=A)
3. Acceptor回应 Logon(35=A)
4. 双向心跳 Heartbeat(35=0)
5. 发送 Logout(35=5) 结束
```

### 5.5 FIX在中国券商中的实际架构

```
上游业务系统(App/Web/量化)
    ↓ FIX 4.4 NewOrderSingle
【FIX解析层 → 市场识别 → 协议适配层】
    ├── STEP适配器(上交所 600xxx/688xxx)
    ├── BINARY适配器(深交所 000xxx/300xxx)
    └── OCC适配器(港交所)
    ↓ 交易所原生协议
【交易所网关/报盘机】
    ↓
沪深港交易所
```

> FIX在中国**不直接对接交易所**（交易所用私有协议），而是券商内部的**统一订单转换层**。

### 5.6 QuickFIX要点

- QuickFIX/J基于**MINA框架**（NIO异步网络）
- `SessionID`唯一标识每个会话
- `SessionTimerTask`实现自动重连、心跳、序列号维护
- **注意**：FIX只是传输协议，实际对接必须获取交易所具体接口文档
