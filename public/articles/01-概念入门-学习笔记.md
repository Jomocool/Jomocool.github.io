## 一、《交易系统：更新与跨越》核心要点

**作者**: 武剑锋（时任上交所技术开发部总监）| **出版**: 2011年 | **地位**: 中国第一部系统研究证券交易系统的专业著作

### 1.1 核心架构设计

#### 分层架构（金字塔型）
```
[接入层] ← → [核心层]
    ↑
外围系统（客户端、券商、行情等）
```
- **接入层**: 外围系统不能直接访问核心层，必须通过接入层代理。承担**汇聚与路由**功能
- **核心层**: 交易撮合、订单处理等核心逻辑
- **通信协议**: TCP/IP，消息报文形式

#### 两种通信模式
| 模式 | 用途 | 特点 |
|------|------|------|
| 请求/响应 | 委托发送、登录等 | 同步应答 |
| 订阅/广播 | 成交确认推送 | 异步推送 |

### 1.2 核心设计原则

- **消息驱动**: 消息在每个节点存储并加标记，后台处理需**幂等**
- **"打包"机制**: 时间片到（~10ms）或收集足够请求后批量处理 → 10个请求打包，吞吐量提高约10倍
- **高内聚低耦合**: 模块正交，一个模块只做一件事
- **无单点设计**: 越核心的系统，设备接入越少，关系越简单
- **防重登录**: 64位整数Cookie + 双向心跳
- **"为了将来丢弃而现在建设"**: 持续重构，减少系统熵值

### 1.3 全书九章结构

1. 全球交易系统调研（纽交所、纳斯达克、泛欧、德交所等）
2. 核心平台选型
3. 技术管理（团队、质量保证、面向变更）
4. **应用架构设计与优化**（核心章节）
5. 系统切换上线
6. 容量管理与事件处置
7. 中国特色的技术支撑体系（融资融券、ETF等）
8. 全球交易系统发展趋势
9. 证券行业宏观技术战略

## 二、OMS（订单管理系统）基础概念

### 2.1 一句话定义

> OMS 是管理交易订单全生命周期的软件平台，覆盖从订单创建、验证、路由、执行到结算的完整流程。它是交易平台的"**中枢系统**"。

### 2.2 五大核心功能

| 功能模块 | 说明 |
|---------|------|
| **订单捕获与验证** | 接收多来源订单（客户端/API/算法），进行合规检查、资金校验、头寸限制等预交易风控 |
| **订单路由** | 将验证通过的订单发至执行场所，支持SOR（智能订单路由） |
| **订单生命周期管理** | 实时追踪订单状态变化（状态机） |
| **头寸与风险管理** | 持续更新头寸，计算实时敞口，执行风控检查 |
| **报告与审计追踪** | 记录每个事件，不可篡改的审计轨迹，满足监管合规 |

### 2.3 订单生命周期状态机

```
PENDING → SUBMITTED → OPEN → PARTIALLY FILLED → COMPLETE
                       ↓              ↓
                   CANCELLED      REJECTED
                       ↓
                    EXPIRED
```

每个状态转换由交易所消息驱动，终态（COMPLETE/CANCELLED/REJECTED）不可再变更。

## 三、OMS 在整体架构中的位置

### 3.1 典型交易数据流（华泰证券实际架构）

```
客户端 → 网关(NGINX) → OMS(订单管理) → DownStream(报盘) → 柜台/交易所
                          ↓
                      订阅中心（推送成交回报）
```

- **网关层**: NGINX代理，路由请求
- **OMS层**: **内存交易系统**，订单验证、风控检查、路由决策
- **报盘层**: 面向不同柜台的适配层，向上屏蔽底层差异

### 3.2 买方视角的定位

```
PMS(投资组合管理) → OMS(订单管理) → EMS(执行管理) → 市场
```

> OMS 处于组合决策与市场执行之间的关键位置。

## 四、OMS vs EMS vs PMS — 必须区分的概念

| 维度 | OMS | EMS | PMS |
|------|-----|-----|-----|
| **主要用户** | 组合经理、合规、运营 | 交易员 | 组合经理、风控 |
| **核心职能** | 管理订单全生命周期 | 最优执行订单 | 管理持仓和组合 |
| **延迟要求** | 毫秒~秒级 | 微秒~毫秒级 | 日级 |
| **市场数据** | 参考数据/日终 | 实时Tick级行情 | 日终数据 |
| **追踪对象** | 订单 | 执行过程 | 持仓和盈亏 |

### 四种系统形态

1. **仅OMS** — 长期持有型机构（养老基金、共同基金）
2. **仅EMS** — 高频策略对冲基金
3. **OMS+EMS（FIX整合）** — EMS管理执行，OMS管订单验证和结算
4. **O/EMS（完全整合）** — 统一架构，消除系统间延迟

### 形象比喻

> OMS 告诉市场"**我要卖出50万股X股票**" → 但**如何**执行（路由、择时、算法选择）是 EMS 的事。

## 六、现代 OMS 技术架构趋势

### 微服务 + 事件驱动
```
OMS服务 → 发布 "order_created" → Kafka
RMS服务 → 订阅 → 风险评估 → 发布 "order_approved/rejected"
结算服务 → 订阅 → 处理成交 → 发布 "settlement_complete"
```

### 核心原则
- **每个服务独立数据库**（不共享DB）
- **幂等性必须保证**（重复事件不创建重复订单）
- **异步优先于同步**（降低延迟）
- **熔断器**防止级联故障
- **事件Schema版本化**（避免一个团队的变更破坏另一个团队）
