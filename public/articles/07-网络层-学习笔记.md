## 一、阶段 6 要解决什么

阶段 5 的撮合引擎是一个「进程内库」，只能被同进程代码调用。阶段 6 让它能**通过网络被访问**：

1. **序列化**：订单/成交/行情消息怎么在网络上传（protobuf）
2. **网络服务**：怎么收发（Asio TCP）
3. **下单接入**：网络消息怎么喂给撮合引擎、回报怎么回（转换层）
4. **行情推送**：盘口怎么高效推给客户端（快照 + 增量）

## 二、项目结构

```
matching-server/
├── proto/trading.proto       # 消息定义：Order/Trade/Snapshot/Increment/信封
├── include/ms/frame.hpp      # length-prefix 帧定界（readFrame/writeFrame）
└── src/
    ├── main.cpp              # protobuf round-trip 验证
    ├── server.cpp            # 撮合服务器（下单 + 行情推送）
    └── client.cpp            # 客户端（下单 + 本地盘口维护）
```

复用阶段 5 的 `matching-engine`：CMake 里直接编译其 `order_book / matching_engine / event_store` 三个源文件，避免跨项目链接依赖。

## 三、四个核心设计

### 1. protobuf 序列化

- 二进制、紧凑：一个订单 23 字节，JSON 要 50+ 字节
- 字段编号 + varint：序列化只存「编号 + 值」，不存字段名
- 一份 `.proto` 生成多语言代码（C++ 引擎 ↔ 未来 Java 柜台互通）

### 2. length-prefix 帧定界（解决粘包拆包）

TCP 是字节流、没有消息边界。约定 `[4 字节大端长度][内容]`：
先读 4 字节拿到长度，再读恰好那么长的内容——无论粘包还是拆包都能还原出完整消息。

### 3. 转换层（proto ↔ 引擎类型）

网络侧用 `ms::proto::*`，引擎侧用 `me::*`，中间手动转换。
这是「C++ 核心 + 其他语言/协议接入」的通用套路：核心类型不依赖网络格式。

### 4. 行情：快照 + 增量

- 订阅时先发一次**完整快照**（客户端建立基准）
- 之后只发**增量**：只含变化的档位，消失的档位用 `qty=0` 表示删除
- **切换时机**：每个连接首次要某标的 → 快照，之后 → 增量
- 增量计算 = before / after 两张快照的 diff（新增 / 变化 / 消失三种）

## 四、关键决策

| 决策 | 原因 |
|------|------|
| protobuf 而非 JSON | 二进制紧凑、有 schema、跨语言 |
| length-prefix 帧定界 | 解决 TCP 粘包拆包，最简单可靠 |
| `oneof` 信封消息 | 一条连接传多种消息（订单/订阅/快照/增量），用 `has_xxx()` 判断 |
| 快照 + 增量 | 全量快照太费带宽，增量只传变化 |
| 复用阶段 5 引擎（直接编译源码） | 避免跨项目链接依赖，清晰自包含 |

## 五、踩坑记录

| 坑 | 原因 | 解法 |
|----|------|------|
| `ms/frame.hpp: No such file` | 重写 CMake 漏了 `target_include_directories(... include)` | 自定义头文件目录必须声明 include 路径 |
| 卖价 1000 不成交 | 卖限价必须 ≤ 买一才能交叉；1000 > 买一 999，只能挂单 | 想穿价吃买盘，卖价要定 998（≤ 买二） |
| `fillIncrement` 逻辑混乱 | 写 diff 时留了冗余循环 | 两遍扫描：先扫 after 找新增/变化，再扫 before 找消失（qty=0） |
