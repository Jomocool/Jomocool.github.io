## 一、项目总览

两个项目分别代表了交易系统的两种典型架构模式：

| 维度 | trading-exchange-system | stock-trade-system |
|------|------------------------|---------------------|

| **架构** | 事件驱动 + 微服务（Spring Cloud + Kafka）| 分层架构 + 多模块（Spring Boot + MyBatis-Plus）|

| **语言** | Java 17 + Spring Boot 3.2 | Java 8 + Spring Boot 2.7 |
| **消息队列** | Kafka（核心数据管道）| RocketMQ（异步通知） |
| **数据库** | 内存撮合 + DB持久化 | MySQL + MyBatis-Plus（CRUD为主）|

### 2.2 撮合引擎（MatchEngine）—— 核心源码分析

```java
// 类结构
MatchEngine {
    OrderBook buyBook;    // 买盘（TreeMap，价格从高到低）
    OrderBook sellBook;   // 卖盘（TreeMap，价格从低到高）
    BigDecimal marketPrice;  // 最新成交价
}
```

**撮合算法流程：**

```
1. 收到Taker订单
2. 根据买卖方向，选择对手盘（买→卖盘，卖→买盘）
3. 循环匹配：
   a. 获取对手盘第一档（最优价）
   b. 价格是否可成交？（买单价≥卖一价 / 卖单价≤买一价）
   c. 如果不可成交 → 退出循环
   d. 以Maker价格成交
   e. 成交量 = min(Taker未成交量, Maker未成交量)
   f. 更新双方状态（完全成交→移出订单簿 / 部分成交→更新余额）
   g. Taker完全成交 → 退出循环
4. 如果Taker还有剩余 → 放入对应订单簿（成为新Maker）
```

**关键设计：**

| 设计点 | 实现 | 原理 |
|--------|------|------|
| **价格优先+时间优先** | `TreeMap<OrderKey, OrderEntity>` | Buy: 价格高→低排序; Sell: 价格低→高排序; 同价按sequenceId排序 |
| **对手盘价格作为成交价** | `this.marketPrice = makerOrder.price` | 确保成交价合理（Taker被动接受Maker报价） |
| **BigDecimal金额计算** | 所有价格/数量用BigDecimal | 避免浮点数精度问题（金融铁律） |
| **增量成交均价计算** | `calculateAvgFillPrice()` | 不重算全部成交，增量更新O(1) |
| **内存订单簿** | TreeMap纯内存 | 避免撮合路径上的IO，微秒级延迟 |

### 2.3 订单簿（OrderBook）—— 数据结构设计

```java
// 订单排序比较器
// 卖盘：价格从低到高
SORT_SELL = (o1, o2) -> {
    cmp = o1.price.compareTo(o2.price);     // 价格优先
    return cmp == 0 ? Long.compare(o1.sequenceId, o2.sequenceId) : cmp;  // 同价时间优先
};
// 买盘：价格从高到低
SORT_BUY = (o1, o2) -> {
    cmp = o2.price.compareTo(o1.price);     // 价格优先（反向）
    return cmp == 0 ? Long.compare(o1.sequenceId, o2.sequenceId) : cmp;
};
```

**OrderKey**: `(sequenceId, price)` 复合键，保证唯一性和排序正确。

### 2.4 TradingEngineService —— 事件驱动的交易处理管线

```
Kafka消息 → processMessages() → processEvent()
    ├── OrderRequestEvent  → createOrder()   → MatchEngine.processOrder()
    ├── OrderCancelEvent   → cancelOrder()   → MatchEngine.cancel()
    └── TransferEvent      → transfer()       → AssetService.tryTransfer()
```

**五个异步线程模型：**

```
主线程(processEvent)：
    ├→ apiResultQueue  → [ApiResultThread] → Redis Pub/Sub → 返回客户端
    ├→ tickQueue       → [TickThread]      → Kafka(Tick Topic) → 行情模块
    ├→ notificationQueue → [NotifyThread]  → Redis Pub/Sub → 实时通知
    ├→ orderBookSnapshot → [OrderBookThread] → Redis Lua脚本原子更新
    └→ orderQueue/matchQueue → [DbThread] → 批量插入MySQL
```

> **关键设计**: 主线程只做撮合（内存），IO操作全部异步化到独立线程，延迟最低。

### 2.5 消息序列号与一致性保证

```java
// 防重复
if (event.sequenceId <= this.lastSequenceId) return;

// 防丢失（阻塞恢复）
if (event.previousId > this.lastSequenceId) {
    events = storeService.loadEventFromDb(this.lastSequenceId);  // 从DB补数据
    for (e : events) this.processEvent(e);  // 追赶
    return;
}

// 防乱序
if (event.previousId != this.lastSequenceId) panic();  // 致命错误
```

> 三个检查形成完整的消息可靠性保证：重复丢弃、丢失追赶、乱序panic。

### 2.6 清算服务（ClearingService）

撮合后必须清算：
- Taker买入 → 冻结USD释放，增加BTC持仓

## 三、stock-trade-system trade-order 模块分析

### 3.1 订单状态机实现

```java
public enum OrderStatusEnum {
    PENDING_NEW(0, "待报"),        // 订单已创建，尚未发送交易所
    NEW(1, "已报"),                // 已发送交易所，等待撮合
    PARTIALLY_FILLED(2, "部分成交"),
    FILLED(3, "全部成交"),
    CANCELED(4, "已撤销"),
    REJECTED(5, "已拒绝"),         // 被交易所拒绝
    EXPIRED(6, "已过期");          // 过期未成交失效
}
```

**两个关键状态判断方法：**

```java
// 终态判断（不可再变更）
isFinalStatus: FILLED / CANCELED / REJECTED / EXPIRED

// 可撤销判断（非终态的活跃状态）
canCancel: PENDING_NEW / NEW / PARTIALLY_FILLED
```

> 这与前两个阶段学到的理论完全对应——FILLED、CANCELED、REJECTED、EXPIRED是吸收态。

### 3.2 订单核心业务逻辑

#### 创建订单
```
1. 参数校验（价格>0、数量>0、类型/方向合法）
2. 订单初始状态: PENDING_NEW
3. 插入订单记录
4. 插入订单日志
5. 发送订单状态变更消息（MQ）
```

#### 撤单流程
```
1. 校验订单存在
2. 校验订单归属（只能撤销自己的订单）
3. 校验可撤销状态（canCancel）
4. 更新状态 → CANCELED
5. 插入订单日志
6. 发送订单状态变更消息
```

#### 成交回报处理（processOrderFill）— 核心
```
1. 校验订单存在且股票代码/方向匹配
2. 创建成交明细(OrderItem): 成交号、价格、数量、手续费
3. 更新订单：
   - 新增已成交数量 = 原已成交 + 本次成交
   - 新增平均成交价 = 增量计算（O(1)，不重算全部）
   - 新状态 = (已成交==总数量) ? FILLED : PARTIALLY_FILLED
4. 插入订单日志
5. 发送订单状态变更消息
```

### 3.3 AvgPx增量计算 —— 生产级实现

```java
private BigDecimal calculateAvgFillPrice(BigDecimal oldAvgPrice, Integer oldQuantity,
                                         BigDecimal newPrice, Integer newQuantity) {
    if (oldAvgPrice == null || oldQuantity == 0) {
        return newPrice;
    }
    // 总金额 = 原均价×原数量 + 新价×新数量
    BigDecimal totalAmount = oldAvgPrice.multiply(new BigDecimal(oldQuantity))
            .add(newPrice.multiply(new BigDecimal(newQuantity)));
    // 新均价 = 总金额 / 总数量，保留3位，四舍五入
    return totalAmount.divide(new BigDecimal(oldQuantity + newQuantity), 3, RoundingMode.HALF_UP);
}
```

> 这个实现完全符合第二阶段学到的设计原则：**BigDecimal精度、增量计算O(1)、禁止float/double**。

## 五、关键代码级收获

### 5.1 金融计算铁律

| 规则 | 原因 | 代码示例 |
|------|------|---------|
| 金额用 BigDecimal | 避免浮点精度丢失 | `BigDecimal price` |
| 禁止 float/double | 0.1+0.2≠0.3 | 全项目无float/double |
| 增量计算平均值 | O(1)复杂度，避免全量重算 | `calculateAvgFillPrice()` |
| RoundingMode明确指定 | 确定舍入策略 | `HALF_UP`、`UP` |

### 5.2 订单处理的并发考虑

- **trading-exchange-system**: 单线程事件处理（按sequenceId顺序），天然无并发问题
- **stock-trade-system**: `@Transactional` + 乐观锁（version字段），适合DB场景

### 5.3 日志追溯

两个项目都在订单状态变更时记录完整的日志链：
```
OrderLog: (orderId, beforeStatus → afterStatus, content, operationTime, operatorUserId)
```
这是金融合规的基本要求——每笔订单的每个状态变更都必须可追溯。

### 5.4 消息幂等

- 两个项目都通过业务ID（orderId/sequenceId）进行幂等校验
- trading-exchange-system 通过 `sequenceId <= lastSequenceId` 实现消息级幂等
- stock-trade-system 通过订单状态机终态判断实现业务级幂等
