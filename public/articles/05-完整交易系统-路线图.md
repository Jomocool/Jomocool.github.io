# 完整交易系统建设路线图

> 日期: 2026-08-14 | 定位: 长期项目 · 从 OMS 扩展到完整交易系统
> 目标: 接近生产水平的模拟交易系统，作为面试可深入讲解的项目

---

## 一、目标与定位

前四个阶段完成了「概念 → 架构 → 源码 → 简化版 OMS」的入门闭环。
现在把目标升级为**实现一套尽可能完整的交易系统**，覆盖：

```
网关 Gateway → OMS → 风控 Risk → 撮合引擎 Matching Engine → 行情 Market Data → 清算 Clearing
```

**关键概念——柜台（Counter）**：券商侧的「网关 + OMS + 风控 + 清算」合起来就是**柜台系统**，
即券商的核心交易中台，管账户、资金、持仓、订单、成交；交易所侧的「撮合引擎 + 行情」独立。
本项目实质是 **「模拟柜台（券商侧）+ 模拟交易所（撮合侧）」** 的完整闭环，最终交付物就是一个
**模拟柜台（仿真柜台）**——量化/联调场景的高频术语。

> 行业背景：柜台分「集中柜台」（功能全、毫秒级，恒生/金证）与「极速柜台」（功能精简、微秒级，华锐/宽睿，服务量化）。

**定位**：一个人做不出真生产系统，但可以做到「**关键路径接近生产、整体链路完整可跑**」。
面试时最有分量的不是"我用了某框架"，而是「**我为什么这么设计、踩了什么坑、性能怎么测**」。

## 二、完整系统架构蓝图

> 图中「网关 + OMS + 风控 + 清算」= **柜台系统（券商侧）**；「撮合引擎 + 行情」= **交易所侧**。

```
                       ┌───────────────┐
                       │  客户端 / 策略  │
                       └───────┬───────┘
                               │ FIX / 私有协议
                       ┌───────▼───────┐
                       │   交易网关      │ ← 会话管理、协议转换、订单路由、重传
                       │   Gateway     │
                       └───────┬───────┘
                               │
                ┌──────────────┼───────────────┐
                │              │               │
           ┌────▼─────┐   ┌────▼─────┐   ┌─────▼─────┐
           │   OMS    │   │  风控     │   │   行情     │
           │ 订单管理  │   │  Risk    │   │ MarketData│
           └────┬─────┘   └──────────┘   └─────┬─────┘
                │                               │ 快照/增量推送
                │           ┌───────────────────▼─────┐
                └──────────▶│  撮合引擎 Matching Engine  │
                            │  订单簿 + 撮合 + 成交回报    │
                            └───────────┬───────────────┘
                                        │ 成交/行情
                            ┌───────────▼───────────────┐
                            │   清算结算 Clearing        │
                            │  资金 + 持仓 + 对账         │
                            └───────────────────────────┘
```

**核心数据流（下单）**：
`客户端 → 网关 → OMS → 风控 → 撮合引擎 → 成交回报 → OMS → 持仓 → 清算`

**行情数据流**：
`撮合引擎 → 行情系统 → 推送 → 客户端`

## 三、技术选型

| 层 | 选型 | 理由 |
|----|------|------|
| 撮合引擎 / 行情 / 网关（低延迟核心） | **C++17/20** | 低延迟关键路径，也是面试最硬核的部分 |
| 网络 | **Asio**（standalone） | 行业主流 Reactor/Proactor，C++ 标准网络库基石 |
| 序列化 | **protobuf** + 自定义二进制协议 | protobuf 通用；二进制协议体现协议设计能力 |
| 消息队列（分布式阶段） | **Kafka** | 金融行业事实标准，事件驱动核心 |
| 持久化 | SQLite（单机）→ PostgreSQL（分布式） | 先轻后重 |
| 业务层（OMS/风控/清算） | 先 C++ 保持统一，跑通后可选 Java 化 | 一个人做先减上下文切换 |

> **语言决策**：建议**核心链路（撮合/行情/网关）全程 C++**，这是面试技术深度的主战场；
> 业务层先用 C++ 保持一致，等核心跑通后再考虑对照 stock-trade-system 做 Java 版（那时已有清晰参照）。

## 四、分阶段路线

> 编号接续前四阶段（1-4 已完成）。每阶段独立可交付、可验证，不追求一步到位。

### 阶段 5：撮合引擎生产化 + 交易机制（核心 · 最重要）

**目标**：把单标的简化撮合引擎升级为接近生产的多标的引擎，并实现完整交易机制。

- **多标的**：`symbol → OrderBook` 映射，替代单实例买/卖盘
- **并发模型**：全局锁 → **按标的/价格档位细粒度锁**（或 sharding），理解锁竞争与延迟
- **成交回报**：事件流 + 持久化（**事件溯源**，支持回放重建状态）
- **性能基准**：吞吐（orders/s）、延迟（P50/P99），对比全局锁 vs 档位锁
- **交易机制**：连续竞价 + **集合竞价**（开盘价确定）+ 收盘；涨跌停、停牌（可选）

**交付物**：可 benchmark 的多标的撮合引擎 + 性能报告
**面试亮点**：锁粒度设计、无锁数据结构、基准测试方法论、集合竞价撮合规则、交易时段状态机

### 阶段 6：网络层 + 序列化 + 行情

**目标**：让撮合引擎能通过网络被访问，产出并推送行情。

- **序列化**：protobuf 定义订单/成交/行情消息
- **网络服务**：Asio TCP 服务端，订单接入、回报推送
- **行情**：Level 2 快照 + **增量推送**（快照与增量的切换时机）
- **IO 模型**：理解 epoll / reactor，连接管理、粘包拆包

**交付物**：通过 TCP 下单、收回报和行情的引擎
**面试亮点**：IO 多路复用、序列化选型、行情增量 vs 快照、背压处理

### 阶段 7：交易网关 + FIX 协议

**目标**：实现对接撮合引擎的网关，理解行业标准协议。

- **FIX 子集**：NewOrderSingle / ExecutionReport / OrderCancelRequest
- **会话层**：Logon/Logout、心跳、**序号管理与重传**、断线恢复
- **可靠性**：订单路由、幂等去重、故障恢复

**交付物**：FIX 网关，客户端经 FIX 下单到自己的撮合引擎
**面试亮点**：FIX 会话层/应用层、可靠性、重传/恢复、协议状态机

### 阶段 8：账户资金模块（柜台基础）

**目标**：补齐柜台核心的「账户 + 资金」能力（此前只有持仓，缺资金维度）。

- **Account**：总资金 `totalAmount`、冻结资金 `frozenAmount`、可用资金 `availableAmount`
- **资金变动**：入金 / 出金
- **下单联动**：买入冻结资金 → 成交扣款 → 撤单解冻（与持仓 freeze/unfreeze 完全对称）
- **资金流水**：每笔资金变动可追溯、可对账

**交付物**：带资金维度的柜台核心，下单前可校验「可用资金是否充足」
**面试亮点**：资金冻结/解冻、幂等记账、资金一致性、与持仓的对称设计

### 阶段 9：分布式改造（事件驱动）

**目标**：单机 → 微服务，事件驱动解耦。

- **Kafka** 作为事件总线
- **拆分**：网关 / 柜台（账户+OMS+风控）/ 撮合 / 清算为独立进程，事件驱动通信
- **CQRS**：写模型（撮合）与读模型（查询/行情）分离
- **一致性**：幂等、至少一次/精确一次、乱序处理

**交付物**：多进程微服务，经 Kafka 串联
**面试亮点**：分布式一致性、幂等、CQRS、消息驱动、Kafka 分区/顺序保证

### 阶段 10：风控系统深化

**目标**：完整的三层风控。

- **预交易**：限额、价格、持仓、资金、集中度（阶段 8 的资金维度在此纳入）
- **事中**：撤单速率、自成交检查、实时风险敞口
- **事后**：日终对账、风险报告

**交付物**：可插拔的风控规则引擎
**面试亮点**：风控架构、实时风控延迟、规则引擎设计

### 阶段 11：EMS 算法交易（父子订单）

**目标**：实现执行管理，支持算法单拆分（对应阶段 2 学过的 TechNova 父子订单）。

- **父单/子单**：一个父单拆成多个子单，父子状态联动
- **算法**：TWAP（时间加权）、VWAP（成交量加权）
- **执行控制**：子单进度跟踪、父单撤单联动、未完成量回收

**交付物**：能下「TWAP/VWAP 算法单」的 EMS 模块
**面试亮点**：算法交易、订单拆分、父子状态机、执行进度、AvgPx 计算

### 阶段 12：清算结算 + 对账 + 历史数据

**目标**：资金与持仓的最终一致性，以及历史数据沉淀。

- **数据模型**：订单/成交/持仓/资金流水
- **对账**：内部对账 + 与"交易所"对账
- **日终清算**：批量任务、事务边界
- **历史数据**：成交历史、行情 K 线（时序存储 + 查询）

**交付物**：持仓/资金可查询、可对账，历史数据可回溯
**面试亮点**：数据一致性、对账逻辑、事务边界、时序数据存储

### 阶段 13：监控 + 模拟柜台端到端

**目标**：可观测的、端到端可演示的**模拟柜台（仿真柜台）**。

- **可观测性**：结构化日志、指标（延迟/吞吐）、告警、健康检查
- **模拟行情生成器**：随机游走/档位生成
- **端到端链路**：行情 → 下单 → 网关 → OMS → 风控 → 撮合 → 回报 → 持仓 → 清算
- **柜台对外接口**：模拟真实柜台的 API（账户/资金/持仓/下单/撤单/成交查询）
- **可视化**：盘口、成交、持仓（Web 或终端 UI）

**交付物**：一个能演示「开户 → 入金 → 下单 → 成交 → 持仓 → 清算」全流程的模拟柜台
**面试亮点**：系统架构全局观、完整可演示、故障注入、可观测性、柜台 API 设计

## 六、面试可讲清单（沉淀目标）

每完成一个阶段，应能就以下维度深入回答：

1. **设计为什么**：为什么档位锁而不是全局锁？为什么事件溯源？
2. **踩过的坑**：锁竞争、粘包拆包、FIX 重传、Kafka 顺序、幂等
3. **性能怎么测**：benchmark 方法、延迟分位、瓶颈定位
4. **可扩展性**：多标的、多实例、水平扩展
5. **可靠性**：断线重连、消息重放、对账兜底

> 原则：**每个阶段先跑通（能演示），再深入（性能/可靠性），最后沉淀（写笔记 + 面试话术）**。
